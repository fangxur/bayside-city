# 账号、多设备与版本更新

## 玩家怎么用

- 新玩家：首页选择“登录 / 注册账号”，填写账号名、密码和玩家名字，下载账号恢复卡。也可先用游客身份单机游玩；游戏右上角和存档菜单始终提供账号入口。
- 老玩家：先在原来使用的浏览器进入合作大厅，选择“绑定账号”。保留原玩家 ID、城市、房主权限、成员资格、建设日志和待确认操作；绑定成功后旧身份凭据失效。
- 如果旧玩家只剩导出的身份 JSON：在登录页展开“备份或恢复玩家身份”，导入后绑定。不要清理原浏览器数据。
- 单人城市：登录后新建的城市自动归当前账号，在本机模拟，定期同步到服务器。“我的城市”统一列出单人城市和合作城市。已有游客存档需先打开，再点“绑定这座单人城市到账号”；原游客存档保留，绑定不会开启多人权限。
- 第二台设备：登录同一服务器上的相同账号，从“我的城市”继续单人城或合作城。单人城请先在原设备确认“已保存到账号”；合作城无需再次使用邀请码，也不多占成员名额。
- 邀请朋友：朋友使用自己的账号接受邀请。不要把自己的密码或恢复卡当作邀请发送。
- 合作城可多设备同时建设，服务器检查地块与余额，统一保存结果。同一笔待确认操作仍使用原命令 ID 重试，避免重复扣费。
- 单人城采用版本检查，两台设备保存冲突时不会覆盖服务器新进度。本机版本可以另存新城；选择服务器版本会先将本机版本另存并下载备份。断网时保留本机进度，原账号恢复连接后继续同步。
- 在“账号与我的城市 → 账号与登录设备”查看登录记录、退出其他设备、修改密码。每个设备的登录有效期为 30 天，退出当前账号不影响其他设备。
- 忘记密码：用“忘记密码”输入账号名与恢复码。恢复码只能用一次，成功后下载新恢复卡。修改密码、恢复账号都会让之前的所有设备会话失效。
- 同一浏览器不同标签页共用登录状态。切换账号后，其他标签页退出原账号的城市；账号单人存档和待确认操作按原账号隔离，重新登录原账号后恢复。游客存档不自动归给下一位登录者。

第一版不依赖短信、邮件、微信。不支持自动合并不同旧玩家的身份，也不按同名猜测归属。没有密码和恢复码时不能自助找回。账号属于这个游戏服务器；本机、局域网、正式域名使用不同数据库时，账号不会自动互通。

## 数据与权限

账号与城市存在同一个外置 SQLite 数据库中，数据库备份同时包含两者。密码使用带随机盐的 scrypt（N=32768、r=8、p=3）派生，登录令牌与恢复码仅保存哈希。账号登录使用 HttpOnly、SameSite Cookie，HTTPS 下启用 Secure；浏览器本地只保存账号显示信息，不保存密码或账号登录令牌。注册绑定采用数据库事务，旧身份凭据在绑定成功时撤销。

账号单人城市保存在 `solo_cities`，只有所属账号能列出、读取或保存；它不进入合作模拟时钟。单人同步使用持久化待发送记录、幂等请求 ID 和版本比较，服务端验证导入存档后保存。旧版游客检查点沿用原本地键；账号检查点与待同步存档使用账号独立键。数据库迁移只新增表与索引，不改写已有合作城市。

密码处理参考 [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)；Cookie 会话与同源检查共同防止其他站点提交操作。登录限速适用于好友测试规模：同一账号最多 12 次尝试/15 分钟，恢复最多 6 次；反代后的来源还受整体限流。暂不面向大规模公开运营。

## 固定目录

```text
/www/bayside-city/
  production.env          # 固定配置，不放发布包里
  app -> releases/版本号   # 宝塔始终启动这个固定路径
  releases/               # 各版程序和各自的依赖
  uploads/                # 上传 tar.gz 的位置
  update-state.json        # 更新准备/切换/验收记录
/www/bayside-data/cities.sqlite  # 正式城市、账号、日志
/www/bayside-backups/            # 日常备份
  before-update/                # 每次升级/回退前的长期备份，不参与自动清理
```

宝塔项目目录保持 `/www/bayside-city/app`，启动命令保持：

```sh
node --env-file=/www/bayside-city/production.env server.mjs
```

运行用户 www，端口 4173。保持单个进程；不要同时用宝塔与 PM2 启动两份。正式数据库不能放在 app 或 releases 里。程序目录只需 www 可读；数据目录需 www 可写。

## 第一次使用更新工具

1. 把新发布包上传到 `/www/bayside-city/uploads/`，不要解压覆盖 app。
2. 从新包里只取出更新工具，放到独立目录。将下面 `新版文件名.tar.gz` 换成实际名字：

```sh
mkdir -p /www/bayside-city/installer
cd /www/bayside-city
tar -xzf uploads/新版文件名.tar.gz -C installer --wildcards 'deploy/*'
node installer/deploy/baota/update.mjs prepare /www/bayside-city/uploads/新版文件名.tar.gz
```

工具会检查包内逐文件 SHA256、安装依赖、检查语法，再用正式数据库的副本试运行迁移和完整性检查。此时旧版继续服务。SHA256 还可与提供的 `.sha256` 文件比对，确认上传完整。

3. 看到“准备完成”后，让玩家暂停建设并离开城市，在宝塔停止 **bayside-city** 项目。然后运行：

```sh
node /www/bayside-city/installer/deploy/baota/update.mjs activate
```

工具确认 4173 已停止，备份最新正式数据库，再次试迁移副本，保留旧 app 为一个历史版本，并把 app 切到新版。不会恢复、覆盖、清空正式数据库。

4. 在宝塔启动项目，再执行：

```sh
node /www/bayside-city/app/deploy/baota/update.mjs verify
```

本机和 HTTPS 域名的版本检查均通过后，刷新游戏，用原浏览器绑定账号，再到另一台设备登录验证。

## 后续更新：一个固定命令

首次把项目内的 `deploy/baota/update.sh`（或单独提供的同名文件）上传到服务器 `/www/bayside-city/update.sh`。这个入口保留在 app 外，不会因版本切换消失。使用 bash 运行，无需设置可执行权限。

以后本地改完代码并通过测试后，运行 `npm run release`，把新的 `bayside-时间戳.tar.gz` 上传到 `/www/bayside-city/uploads/`。保留原包名，不必删除旧包，不要直接解压覆盖 app。上传完成后，在宝塔终端运行：

```sh
bash /www/bayside-city/update.sh
```

同一条命令分三次运行，每次完成一个阶段后自动退出：

1. 第一次运行：自动选择最新上传的包，检查文件、安装依赖、用存档副本试迁移。完成后保存 `prepared` 进度并退出。去宝塔停止项目。
2. 重新打开终端，再运行同一命令：读取已准备的版本，确认停机、备份最新存档、切换程序。完成后保存 `awaiting-verification` 进度并退出。去宝塔启动项目。
3. 重新打开终端，再运行同一命令：检查本机服务和游戏域名，验收成功后保存 `verified` 状态。

每个阶段之间可以自由切换页面、关闭终端；不需要按回车接续，也不依赖原来的终端会话。进度保存在 `update-state.json`，不会重新安装已经准备好的版本。

仍需在宝塔点一次停止、一次启动。向导不另外创建 Node 进程，避免与宝塔进程守护冲突。任何检查不通过都会停止，不会自动覆盖数据库，也不会自动降级。

- 已是最新上传版本：直接提示，无需停机。
- 已准备/已切换：先完成这次更新，不会被新上传的包打断。
- 等待宝塔操作时：向导已经退出，不会占用锁。重新执行相同命令继续。
- 忘记先停止项目：底层工具拒绝切换，仍保留准备好的版本；忘记启动或启动尚未完成：保留待验收状态，启动成功后重试。
- 终端在 Node 命令执行过程中断开：先确认后台检查/切换是否仍在进行；若提示锁存在，按下面的异常处理检查，不要重复启动更新。
- 更新完成后：刷新游戏页面。离线客户端重连后按原命令编号核对未确认操作。

非默认安装目录可以作为唯一参数传入，例如 `bash update.sh /自己的项目目录`。已有逐步命令仍可手工使用：`prepare 发布包路径` → 宝塔停止 → `activate` → 宝塔启动 → `verify`。

## 出问题时

- 旧向导提示 `.update-wizard-lock`：把修复后的独立 `update.sh` 覆盖上传到 `/www/bayside-city/update.sh`，再运行同一命令。新版不再使用外层向导锁，不需要删除旧标记，也不必重新上传已经准备好的游戏包。真正写入数据时仍由底层 `.update-lock` 保护，不能绕过。
- prepare 失败：当前 app 未切换，旧服务照常运行。根据错误修复后重试。
- activate 提示进程仍运行：在宝塔停止项目，不要手工同时再开一份 Node。
- 启动失败或 verify 失败：先看宝塔“项目日志”。需回退时，停止项目，再用**新包中的更新工具**执行 `rollback`，随后启动并验证。

```sh
node /www/bayside-city/installer/deploy/baota/update.mjs rollback
```

后续更新也可使用当前 app 内的工具。回退仅切程序，保留最新城市与账号；回退前也生成备份。若已经创建账号，脚本会拒绝回退到没有账号功能的最初旧版，避免账号无法访问。此时应使用修复版程序。

整库恢复不是普通版本回退：它会回退所有人的城市和账号，只应在停机、确认备份时间、保留当前库后人工操作，遵循 README 的离线恢复步骤。不要把旧数据库直接覆盖到仍运行的服务，也不要删除 SQLite 的 WAL/SHM 文件来“解决冲突”。

若终端在实际检查、备份或切换过程中异常断开，进程可能仍在后台运行；先检查更新进程、app 指向与 `update-state.json`。只有确认没有更新进程后，才用 `rmdir /www/bayside-city/.update-lock` 清理底层工具的空锁目录；新版入口不会自动删除或绕过这个锁。旧版 `.update-wizard-lock` 标记不影响新版入口，无需清理。不要删除 releases、备份或数据库来解锁。长期备份需要自行安排异机复制与保留策略。

开发验证：`npm test` 检查游戏逻辑与向导分阶段恢复；生成发布包后，可运行 `npm run test:update -- /绝对路径/发布包.tar.gz`，它只在新建的临时目录和随机本机端口中演练重新打开终端、旧向导锁恢复、旧身份迁移、两次程序更新、停机保护、回退以及单人/合作城市进度保留，并在结束时清理测试目录。
