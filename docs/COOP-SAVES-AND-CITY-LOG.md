# 合作城市：存档、操作冲突与建设日志

状态：第一版已实现（2026-09-30）。适用范围：2～4 人好友共建。下文保留完整目标设计，以下列表说明当前实际交付与差异。

当前交付：

- 合作大厅、邀请加入、4 人成员上限、房主权限与移除成员、玩家身份导出/恢复。
- 全部城市写入改经统一命令入口；服务器推进模拟，每笔事务保存完整正式状态、命令回执和建设日志。
- 使用 Node 内置 SQLite（WAL + FULL 同步），以数据库写事务串行化，包括多进程重复 tick 防护。无需额外数据库服务；PostgreSQL 仍是后续扩容选项。
- 已保存状态和短期历史使用 gzip 压缩；保留最近 512 个正式版本供冲突预检和撤销。当前用服务器上可信的旧版本与最新版本重新预检，比对目标结构、完整影响范围与报价，不额外发放 quoteToken。
- 以每 1.5 秒拉取完整最新状态替代 WebSocket 增量广播；按单调版本防止旧响应覆盖新状态，省略未变化的状态载荷。此版没有增量变更重放和 7 天精细恢复。
- 自动检查点、每日存档、纪念存档、导出、复制新城、恢复前备份及 epoch 隔离已接入。恢复确认绑定当时的正式版本；期间有新进展必须重确认。
- 完整 SQLite 备份每 5 分钟执行并检查完整性；仍需把备份复制到独立存储才能覆盖磁盘级故障。
- 日志按玩家/文案筛选、每 3 秒刷新、范围定位与较早记录分页。地块占用提示、好友光标、规划区域、大额建设投票尚未加入。
- 已支持账号名＋密码、恢复码找回、多设备会话与旧玩家绑定；原 ID、日志、权限和命令回执保留。账号与发布更新的实际使用步骤见 [账号、多设备与版本更新](ACCOUNTS-AND-UPDATES.md)。

已验证：两个游戏页面共享建设结果、余额和日志；事务故障回滚、100 次重复请求、进程在提交前后被强制结束、并发占地/预算冲突、旧版本撤销与恢复、重复节庆领奖、权限、备份恢复和网络回执丢失都有自动化用例。

## 1. 玩家能依赖的规则

合作城市有一份服务器上的正式进度。玩家提交的是“修这段路”“移动这栋建筑”等操作，不是各自修改过的整座城市存档。

- 两人建不同区域，只要当前资金和建设条件允许，两次操作都能保留。
- 同一地块或建筑发生冲突，先成功提交的一次生效，另一次说明原因并保留规划预览，不扣费、不覆盖。
- 界面显示“已保存”必须以服务器持久化成功为依据。发送成功、收到请求、内存更新都不等于已保存。
- 重复点击、刷新重发、断线重试，同一次操作最多扣款和生效一次。
- 合作城市断线后可浏览，暂停提交建设；本地旧进度不得在重连时覆盖正式进度。
- 撤销自己的建设不能撤销他人的建设。恢复全城历史版本属于另一项管理操作。

这些规则解决的是冲突的安全处理，并不承诺两个人争用同一位置时都能成功。

## 2. 当前代码需要怎样调整

| 当前实现 | 合作模式调整 |
| --- | --- |
| `src/main.js` 的 `autosave()` 把整城序列化到 localStorage，最多保留三个检查点 | 保留为单人功能；合作模式读取服务器进度，本地只缓存已确认的副本及待确认命令 |
| `manualSave()`、导入和读取存档直接替换本地城市 | 合作模式“保存”创建服务器纪念存档；导入默认创建新城市，不能覆盖当前合作城市 |
| `advance()` 在每个浏览器里运行 `sim.tick()` | 合作城市仅服务器推进人口、月结、施工、事件和随机数 |
| `CitySimulation.undo()` 用 `_undo.state` 恢复整城 | 合作模式禁用该入口，改为服务器校验的撤销命令 |
| `serialize()` 精简派生字段，`deserialize()` 校验、重算且迁移旧地块 | 作为旧单人存档导入接口保留；另设版本明确、读入不改写原始状态的服务器存储格式 |
| `server.mjs` 仅处理 GET/HEAD 静态文件请求 | 新增独立合作服务、身份验证、成员权限、持久化与实时同步；不把它误当作现成联机后端 |

所有会改变城市的操作必须走同一入口：建设、拆除、移动、旋转、升级、全城道路升级、命名、税率、贷款、设施开关、消防预算、事件支持、节日竞猜与领奖、模拟推进。只迁移建设按钮会留下重复领奖或财政覆盖的问题。

镜头、图层、建筑分类过滤、面板展开、夜景偏好仍属个人设置。打开详情或暂停本地渲染不能暂停大家的城市；城市暂停与速度是有权限的共享命令。

## 3. 一次操作的完整过程

1. 玩家拖出建筑或道路，先显示本地预览。涉及花费、拆除的最终方案向服务器请求预检。
2. 服务器生成短时有效的预检凭据，绑定玩家、城市分支、操作参数、目标对象/地块版本、完整影响范围和报价。不能信任客户端自行声明“只影响这些格子”。
3. 玩家确认后提交命令，带唯一 `commandId`、预检凭据和可接受价格。界面显示半透明预览与“正在保存”，正式余额暂不扣减。
4. 服务器在该城市的事务内重新检查身份、权限、分支、命令是否重复、目标版本、当前道路/供货/解锁/资金条件。把命令应用到工作副本，不能提前改动正式内存状态。
5. 一次数据库事务写入新的正式城市状态、递增版本、操作结果、变更记录和建设日志。任何一步失败则全部不生效。
6. 事务成功提交后才发布新状态、返回成功并广播给其他玩家。客户端据此更新建筑、余额、日志和“已保存”状态。

命令建议字段：`cityId`、`epoch`、`commandId`、`baseRevision`、`type`、`payload`、`quoteToken`。操作者从服务器验证过的身份取值，不采信请求里的玩家姓名或角色。

成功结果含 `commandId`、`epoch`、`revision`、实际费用、影响对象和日志 ID。失败结果使用明确代码，例如 `TARGET_CHANGED`、`INSUFFICIENT_FUNDS`、`QUOTE_EXPIRED`、`CITY_RESTORED`、`PERMISSION_DENIED`，附可直接展示的中文解释。

### 顺序与去重

- 一座城市的写入，包括系统 tick，按服务器接受顺序执行；不使用玩家设备时间决定先后。
- 第一版每城一条处理队列，数据库仍锁定城市记录并校验期望版本。即使误启动第二个服务进程，也不能从各自旧内存写回覆盖。
- 任何内存副本都必须与数据库当前版本匹配，不匹配就加载最新状态重新计算；不能拿到锁后继续使用过期副本。
- 幂等键为 `(cityId, epoch, actorId, commandId)`。相同键与相同参数返回原结果，参数不同则拒绝。
- 去重结果和城市变更同事务提交。已处理命令的精简去重凭据保留至对应城市分支删除，不能随短期日志清理，导致很久后的重试再次扣费。
- 系统 tick 使用分支和目标 tick 组成唯一命令标识。两个定时任务同时触发，也只能推进一次。

## 4. 常见冲突的具体体验

| 情况 | 处理 | 玩家看到的提示 |
| --- | --- | --- |
| 两人在不同地块建设 | 各自按最新财政与建设条件校验，依次提交 | 正常建成，两条日志都保留 |
| 同时在一块空地建房 | 第一条成功，第二条拒绝 | “这里刚被小林建了便利小店，换个位置试试。” |
| 两人同时升级同一栋建筑 | 检查目标原等级/编辑版本，第二条不能自动再升一级 | “这栋建筑已升级，查看新等级后再决定。” |
| 一人移动，另一人拆除同一栋建筑 | 检查稳定建筑 ID、原位置与编辑版本，拒绝旧目标操作 | “这栋建筑刚被移动，请重新选择。” |
| 一人移入另一人的待建区域 | 预览不占地；正式提交时检查全部占地 | 提示占地变化，保留未提交预览 |
| 两人都看到资金足够，但合计超预算 | 第二条用扣款后的余额校验 | “刚完成另一项建设，当前资金不足，未扣费。” |
| 一人规划道路，另一人占用了其中一格 | 整条确认方案拒绝并刷新预览 | 显示冲突格，不悄悄少修一截或改价 |
| 全城道路升级时有人新增/升级道路 | 报价绑定明确的道路集合与目标等级；集合变化就重新预检 | 显示新的范围、总价，让玩家再次确认 |
| 供货工厂被关闭、连接道路被拆除 | 提交时按当前城市规则重新检查 | 显示具体缺失条件，不能沿用旧绿灯预览 |
| 掉线前已扣款，成功回执没收到 | 重连查询原命令结果 | 恢复已建成建筑，只扣一次 |

`baseRevision` 用于同步追踪；其他区域发生无关变化不应让所有命令失败。预检凭据绑定相关地块和对象的编辑版本，相关条件变化则重新预检。人口统计更新本身不使所有编辑失效，但解锁、施工状态等真正影响本次操作的条件必须按最新状态重验。

重要实现点：现有 `preview()/build()` 对一批格子可能筛选出其中可改的部分。合作提交必须比对服务器预检的完整方案，禁止验证后静默缩小范围或把坐标上新出现的另一栋建筑当作旧目标。

选中建筑移动时可显示“某某正在操作”，用短时占用提示减少碰撞；它不是数据安全依据。断线会释放提示，真正的正确性仍由版本校验和事务保证。

## 5. 正式进度、历史版本与灾难恢复

### 存储结构

第一版建议采用关系数据库事务存储（例如 PostgreSQL），先用每次提交保存完整当前状态的简单方案；2～4 人规模下先测量 64×64 城市的写入量和耗时，再考虑增量压缩。

| 记录 | 内容 |
| --- | --- |
| `cities` | 城市 ID、当前 `epoch`、单调递增 `revision`、存储格式版本、模拟引擎版本、完整正式状态及校验和 |
| `city_members` | 成员与权限，独立于游戏存档，恢复旧城市不会恢复已移除成员的访问权限 |
| `city_commands` | 幂等键、规范化请求哈希、结果及对应版本 |
| `city_changes` | 每个成功版本的结构化状态变更、前后校验和；系统 tick 也记录 |
| `city_log` | 给玩家看的建设、财政、里程碑和恢复事件，引用同一提交版本 |
| `city_snapshots` | 不可修改的命名快照、版本、分支、创建者和来源信息 |

状态变更、版本、去重结果、变更记录和可见日志必须同事务写入。WebSocket 消息可以在提交之后发送；断线或广播失败通过补拉已提交记录恢复，不通过重新执行操作补广播。

正式进度的自动持久化是每次提交。另按真实时间每 5 分钟生成历史快照，保存最近 24 份；每日另留一份，保存最近 30 天。城市无人在线、暂停且状态无变化时不产生重复快照。人口里程碑和玩家命名的纪念存档单独保留，空间接近上限时明确告知，不静默删除这些纪念存档。

短期变更记录用于断线补齐与区间恢复；可以保留最近 7 天。超出增量保留窗口的客户端直接获取完整正式状态。清理顺序是先写入并验证可恢复快照，再清理不再被恢复区间依赖的变更；可见建设日志和去重凭据不能跟着一起删除。

### 快照内容与读档验证

必须保存地图、建筑稳定 ID、占地与旋转、等级和施工进度、人口、资金、政策、贷款、月份/tick、随机数状态、解锁、事件、节日游戏与领奖状态、游艇状态、统计历史及引擎版本。

服务器恢复格式与旧玩家导出格式分开。明确哪些字段是持久化事实，哪些能纯计算重建；不能简单复用带迁移副作用的 `deserialize()` 当作每次事务的克隆函数。

要求验证 `load(save(state))` 不改变持久化事实及后续模拟结果。迁移先在副本执行，校验成功后才切换。恢复历史版本以快照加**已提交状态变更**为准，不能让新版规则重新执行旧命令，重新开奖、重新扣费或产生另一批随机居民。

### 数据库故障的边界

数据库行锁可以串行化同一城市的写入；事务提交是否已持久化还依赖 WAL 与部署配置。[PostgreSQL 行锁说明](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)、[WAL 说明](https://www.postgresql.org/docs/current/wal-intro.html)。

验收要求：同一持久化存储可用时，进程崩溃或重启不丢失任何已确认提交。存储失败则停止该城写入和模拟推进，显示“保存暂不可用”，不能继续累计看似成功的建设。

整块磁盘或整个区域丢失属于另一层故障，需要独立备份与恢复演练。上线前明确备份恢复点目标；建议备份目标最多丢失 5 分钟、恢复目标 1 小时，必须实测后承诺。若要求机器整体损坏也不丢已确认操作，需要同步复制的持久化部署，不能用异步副本/备份冒充零丢失。恢复到落后版本时切换分支、通知玩家缺失区间，不能悄悄覆盖。

## 6. 断线、重连、多标签页

- 状态条区分“已保存到合作城市”“正在保存 · 1 项”“连接中断 · 只读”“保存暂不可用”，不把本地缓存说成云端已保存。
- 客户端先持久记录命令 ID 和参数再发送；重连先查询结果。结果未知时提示“正在核对”，不要断言失败，更不要生成新 ID 重发同一操作。
- 尚未处理的命令先用原 ID 重新校验。已失效的旧方案返回冲突，让玩家重看预览；断线期间不自动排队一大批建设。
- 每条同步消息携带 `epoch`、`fromRevision`、`revision`。客户端只按连续版本应用；重复的忽略，缺一段就补拉，乱序先缓冲，校验失败则获取完整状态。
- 初次加入返回同一版本的完整状态和续传位置；订阅从该位置开始补发，防止取快照与开始监听之间漏掉建设。
- 重连补发与实时广播使用同样的顺序规则；未补齐前，保持只读。
- 同一账号开多个标签页也视作多个客户端，仍走相同的服务器校验，不能靠 localStorage 互相覆盖。登出或移除成员立即撤销提交和读取权限。
- 最后一个在线成员离开后，服务器在心跳超时后暂停该城；第一版不做离线自动经营、不追赶停服期间的 tick。重新进入从最后持久化 tick 继续。

## 7. 撤销和恢复不是同一件事

**第一版撤销采用保守规则：**只能撤销自己刚完成的、仍是全城最新版本的可逆编辑，并且期间没有其他玩家或系统 tick 提交。服务器校验版本后生成新的撤销记录和新版本，原日志保留并标记“已撤销”。不能在客户端直接恢复 `_undo.state`。

不满足条件时明确提示：“之后已有其他建设或城市进展，不能直接撤销。”玩家仍可用正常移动、旋转、拆除命令调整，按当前规则计费。后续再扩展按对象依赖判断的精细撤销；第一版不冒险回滚跨玩家的交通、人口和财政影响。

**恢复历史城市：**默认先“从这个版本创建新城市”，不会影响大家正在玩的城市。只有房主能执行“恢复当前合作城市”。

恢复当前城市的流程：

1. 展示目标时间、人口、资金和将被回退的建设条数，明确这是全城回退。
2. 在服务器进入维护状态，阻止新提交并通知所有在线玩家。房主确认基于最新版本，期间有变化就重新展示影响。
3. 同事务保存恢复前的不可修改备份，载入已验证快照，递增 `epoch` 和全城 `revision`，记录恢复日志并提交。
4. 旧分支的预检、占用提示和未完成命令全部失效。旧客户端必须重新同步，不能把恢复前的建设重新传回来。
5. 成员权限与审计日志保持不变；恢复不会倒退城市 ID 或复用正式提交版本号。建筑 ID 只在相应分支内解释。

## 8. 城市建设日志界面

入口放在城市菜单与最近动态中。默认显示建设、升级、拆除、重要财政变化、人口里程碑、纪念存档和恢复。每个 tick 都进入技术变更记录，但不刷屏到玩家日志。

示例（实际姓名、价格、坐标必须来自提交结果）：

> 20:14 · 小林建了一座喷泉广场 · 花费 ¥1,400 · 定位
>
> 20:15 · 小周升级了 12 格道路 · 花费 ¥… · 查看范围
>
> 20:18 · 城市达到 1,000 人 · 查看纪念存档
>

支持按玩家、操作类型和时间筛选；连续一次拖拽合成一条，附数量和完整地块列表。日志时间以服务器记录为准，排序以提交版本为准，游戏年月另行显示。

## 9. 实施顺序与上线验收

1. 抽出单人/合作共用的命令接口，梳理全部写入口和只读派生计算，单人继续本地运行。
2. 完成服务器事务、幂等、存档版本、建设日志和故障恢复；先用两个测试客户端验证。
3. 接入实时同步、只读断线态、冲突预览和成员权限，再开放邀请加入。
4. 完成快照、命名存档、恢复分支、导入创建新城及备份恢复演练。

必须通过的场景：

- 同一版本下，两人同时在不同位置建设，结果与余额均正确。
- 同一格、交叠 2×2 占地、移动目的地、同建筑升级/拆除竞争，只能产生合法结果。
- 同时花费接近剩余预算，不透支、不重复扣费；涉及批量操作无部分成交。
- 相同命令发送 100 次，只改变一次，重启后再发仍如此；相同 ID 不同参数被拒绝。
- 提交前、事务中、提交后回执前、广播前分别杀死进程；不出现半笔操作，已提交结果可查询。
- 数据库写入失败时正式内存状态不提前推进，恢复服务后与持久状态一致。
- tick 与建设、月结与扣费、节日领奖与断线重试同时发生，结果可验证且只处理一次。
- 乱序、重复、丢包、加入瞬间有人建设、多标签页与跨设备重连，最终版本和状态校验和一致。
- 建造 A 后另一人建造 B，撤销 A 不得清掉 B；推进模拟后的旧撤销也被拒绝。
- 恢复旧快照后，旧分支命令与缓存不能再次生效；恢复操作本身失败时维持原城市。
- 旧单人存档导入只创建新城市；迁移保留原文件；读写往返及后续模拟结果可重复验证。
- 非成员或已移除成员无法提交/获取数据，客户端改余额、报价、目标列表不会被信任。
- 同时启动两个处理进程，不重复 tick、不覆盖最新状态。
- 从独立备份实际恢复并核对人口、财政、建筑、日志、去重凭据，测量恢复点和耗时。

运行与存档路径见 README 的“好友合作城市”章节。单人存档保持独立；正式公网部署及跨区域灾难恢复尚未验证，不作零丢失承诺。
